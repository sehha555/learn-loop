# 概念累積層 · 階段 1 設計

日期：2026-08-12
狀態：使用者已核可方向與排版（C），待實作

## 背景與目標

使用者的質疑：「入口用 Slide Over 的話，跟開一個 GPT app 多視窗有什麼差？」
答案是差在累積 —— GPT 的對話用完就沉底，這裡每一題要變成留得下來的知識點，
最終長成使用者自己的弱點地圖（LLM wiki）。

三階段路線（本文件只涵蓋階段 1）：

1. **階段 1（本次）**：概念標籤 + 解題當下「你之前也卡過」提醒
2. 階段 2：概念瀏覽頁 + wiki 條目頁（每個概念一頁：解釋、卡過的題目、相關概念）
3. 階段 3：graph 弱點地圖（跨科目概念連成網、常卡的節點標紅）

使用者拍板：「兩個時機都要（解題當下 + 事後回顧），先做解題當下。」

## 方案選擇

採**方案 1：診斷順便抽概念 + 既有概念清單餵回去**。

- 診斷的一次 API 呼叫裡多吐 `concepts` 欄位，不另外打第二次（使用者嫌過慢，
  不能再加等待時間）
- 概念名對齊的機制：把已累積的概念清單（含次數）送進 prompt，要求 AI
  「語意相同就重用既有名字」——避免「和角公式」「和角定理」變成兩個節點
- 「你第 3 次卡了」由 app 端比對計算，不叫 AI 說 —— 次數一定準

否決的方案：獨立抽概念呼叫（多 2-5 秒延遲）、embedding 相似度（沒有概念實體，
接不上階段 2、3）。

## 資料

`Card` 新增 `concepts: [String]`（只有 topic 層使用，子節點不帶）：

- Codable 用 `decodeIfPresent` 預設空陣列，舊資料不會壞
- 筆記類（`is_problem == false`）也照抽 —— 累積不分題型

`CardStore` 新增查詢：

- `conceptCounts() -> [(name: String, count: Int)]`：掃全部 topics 統計，
  最近出現優先排序，取前 50 個供 prompt 使用

## 流程

1. 貼上截圖 → 組 diagnose prompt 時附上既有概念清單（最多 50 個，含次數）
2. AI 回傳診斷 + `concepts`（2-4 個，語意同義時重用清單裡的名字）
3. app 端把新概念跟既有 `conceptCounts()` 取交集 → 生成「你之前也卡過」文案
   （例：「和角公式」你第 3 次卡了）
4. 存檔：concepts 進 topic Card

Schema 變更：diagnose schema 加 `concepts: array of string`（required）。
expand 流程不動。

## 畫面（排版 C：一次一件事）

使用者從三個排版變體選了 C，層級原則：**診斷那一句話是主角**。

topic 卡片由上到下：

1. 標題 —— 退小（caption 級、半透明），只是識別用
2. 診斷句（status）—— 最大字級（headline 級），視覺主角
3. 「你之前也卡過」—— 紅色小字一行，只在有重複概念時出現
4. 「解題步驟」小標（分隔用）+ 編號步驟（既有的 stepBody 呈現）
5. 概念標籤 chips —— 最底、最不起眼；卡過的紅框，新的灰框。
   階段 1 **不可點**（可點進條目頁是階段 2）

## 邊界情況

- 概念清單超過 50 個：取最近的 50 個送 prompt（超過的自然淘汰，
  常卡的概念因為一直出現會一直留在清單裡）
- AI 回空 concepts：正常存空陣列，畫面不顯示 chips 區塊
- 分享浮層（Share Extension）：沙盒與主 app 分開（免費簽章無 App Group），
  各累積各的。主力入口已轉 Slide Over，浮層不特別處理
- 舊資料回溯：不做。已存在的題目沒有概念標籤，維持空白

## 驗證

1. `tune2.py`（scratchpad）跑三種情境（卡住的題目 / 寫完的題目 / 筆記），
   確認：概念名粒度合理、同義概念會重用清單既有名字
2. build 裝 iPad 實測：連續貼兩題同概念的題目，第二題要出現紅字提醒
3. 舊資料開起來不壞（decodeIfPresent 生效）

## 不做的事（YAGNI）

- 概念的手動編輯 / 刪除 / 合併 —— 累積出問題再說
- 概念標籤點擊 —— 階段 2
- graph 視圖 —— 階段 3
- embedding / 相似度搜尋 —— 已否決
